# R17 — Contrat de génération d'applications Vite/Feathers (cadrage de départ)

**Statut : OUVERT — en conception ; aucun générateur multi-UI/SSR/SSG nouveau n'est revendiqué comme implémenté.**

## Point de départ réel

R15 contient déjà le planificateur `examples/basic/scripts/plan-feathers-project.mjs` (`--ui`, `--render`, `--engine`, `--schema`, `--auth`, `--db`, `--transport`, `--json`). Il produit un plan déclaratif sans écrire de fichiers. R16 fournit un exemple **Quasar CLI v2 SSR** entièrement certifié sur Windows, incluant un serveur Feathers v5 séparé, REST, Socket.IO, Pinia SSR et tests Playwright Edge. L'exemple `basic` (Vite + Vue + Pinia) est la base existante pour le générateur côté Vite. **R17 doit étendre ce travail**, ne pas créer un deuxième planificateur concurrent ni remplacer les services de base.

## Objectif R17-r1 — premier générateur utilisable et testable

À partir d'un plan `plan-feathers-project.mjs` validé, produire un squelette de projet **SPA minimal avec une UI** (`quasar2` ou `daisyui`) et un backend Feathers v5, en utilisant des *templates sous contrôle de version* :

1. `--name`, `--dir`, `--ui`, `--render spa`, `--adapter koa|express`, `--transport rest|socketio|both` ; **aucun secret en argument CLI**.
2. Valider nom de package, dossier de sortie, chemin canonique et collision ; refuser les chemins hors sortie, les liens symboliques traversants et l'écrasement silencieux. `--dry-run` doit ne rien écrire ; `--force` ne doit pas détruire un projet existant sans garde-fou ciblé.
3. Générer package, Vite config, boot Feathers, un service `health`, un service `notes`, composant Vue, Pinia côté client et script E2E. L'API métier passe exclusivement par les services Feathers ; Vite n'est pas la base de données.
4. Utiliser une API de service commune aux templates, préserver TypeScript strict, LF et `gitignore` excluant les fichiers et dossiers de travail IA, les secrets et les artefacts locaux. Documentation publique neutre, claire, sans mention de l'outillage de génération.
5. Déclarer explicitement la frontière runtime : service backend autonome en production, Vite middleware uniquement pendant le développement. Les services ne doivent pas être intégrés dans du code client ou du HTML SSR.
6. Tests de déterminisme (même plan -> mêmes fichiers), fail-closed des options inconnues, intégrité des imports, installation, typecheck, build et HTTP CRUD Koa/Express. Edge Playwright GPU disabled : hydratation et CRUD pour les modes supportés.

## Matrice de compatibilité initiale (ne pas prétendre à une prise en charge sans tests)

| UI | SPA | SSR | SSG | Contrat R17 |
|---|---|---|---|---|
| Quasar 2 + `@quasar/app-vite` v2 | À générer puis certifier | **Exemple R16 certifié**, à industrialiser | **GATE BLOQUANT** : ne pas présumer que SSG de Quasar CLI actuel (v3, bêta) est disponible/identique sur la v2.6.2 figée | Quasar CLI pour SSR, ne pas substituer le seul plugin Vite |
| Quasar 2 avec `@quasar/vite-plugin` | À générer puis certifier | Non pris en charge par le contrat actuel | Non pris en charge par le contrat actuel | SPA autonome uniquement, ne pas promettre SSR/SSG |
| daisyUI + Vue/Vite/Tailwind | À générer puis certifier | À implémenter séparément via Vue SSR + Vite | À implémenter via pré-rendu/vite-ssg avec versions validées | Garder Feathers backend distinct ; aucune donnée personnalisée prérendue |
| `daisyui-kit` externe | Planification seule | Non disponible | Non disponible | Ne jamais recopier des ressources ou composants soumis à licence sans droits |

**Important** : la documentation Quasar en ligne évolue ; ses exemples actuellement publiés sont en partie rédigés pour `@quasar/app-vite` v3. Notre référence R16 est **v2.6.2** ; ne pas appliquer automatiquement une configuration v3 sans test de compatibilité spécifique. Le mode SSG Quasar est annoncé en bêta dans la documentation officielle.

## Itérations et portes proposées

- **R17-r1** : générateur SPA Vite/Feathers minimal avec `quasar2|daisyui`, contrôle déterministe des fichiers, tests de contrats, typecheck strict ; partir du planificateur R15.
- **R17-r2** : intégration Quasar CLI SSR en template générable, basée sur R16, inclure `QNoSsr` du champ QInput et état Pinia par requête, certifier compilation + Edge Koa/Express + Socket.IO.
- **R17-r3** : daisyUI SSR et SSG. Vérifier séparément SSR vs build-time SSG, ne jamais exécuter les appels d'auth/notes dans le générateur statique.
- **R17-r4** : qualification des schémas TypeBox/JSON Schema ; Zod après validation réelle des hooks Feathers v5, des erreurs normalisées et des types client.
- **R17-r5** : connexions DB nommées et auth/RBAC seulement avec tests d'isolation serveur, migrations, rollback, secrets en environnement et scénarios négatifs. Aucune exposition publique de la démo non authentifiée.
